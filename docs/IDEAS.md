# Ideas & backlog (non-blocking)

> Parking lot for improvements surfaced mid-build that are **deliberately deferred** — not bugs, not Phase-1 blockers. Each item has a one-line rationale + a rough *when*. Promote an item into `ROADMAP.md` when its phase goes active. Hard, already-made trade-offs live in `DECISIONS.md`; this is the softer "good ideas, later" list.

## AI inside the product (north-star upgrade — partly shipped)
User directive 2026-07-04: make justpaint an **AI-product** — AI features in the product itself, not AI as a dev tool. Priority: **high**. Item (a) has shipped; the other two are still open.

- ~~**Text drawing commands**~~ — **DONE** (Phase A 2026-07-13, the real impl 2026-09-20): an LLM turns natural-language commands into document operations. Our command-based history + vector document were the natural fit they looked like — the model emits shapes, Go expands them into ops, undo/redo comes free, and validation guards the contract. `docs/ASSIST.md`.
- **AI inpainting / draw-completion** — via an external image API; the Node render worker already produces server-side rasters to feed it. Results could come back as raster layers (needs a document extension — a version-safe additive field, format §9) or as vector strokes.
- **Canvas co-author assistant** — an agent that draws alongside the user / critiques / suggests, over the same command seam as text commands.

*Why:* closes the main product gap — a project where AI is **inside** the product, not just a development tool; canvas + LLM integration is a striking demo. *When:* the two remaining items are open — inpainting needs an image API and a raster-layer extension to the document, the co-author needs a UX that is not a one-shot prompt box.

## AI assist (`internal/assist`, shipped `feat/assist-phase-a`)
- **Rate-limit buckets are never evicted** — `RateLimiter` (`server/internal/assist/ratelimit.go`) keys per-user token buckets in an unbounded map with no TTL sweep; fine for Phase A's bounded demo-user set (already flagged in a code comment there). Add TTL eviction, or fold assist into a shared/general rate limiter, when assist scales past a demo. Still open: the in-memory bucket is unchanged and still never evicts — though since 2026-09-20 it is no longer the *only* thing bounding assist, since the daily AI-call ceiling now lives in Postgres (`server/internal/aibudget`, `docs/GAME.md` §4.3) and survives the restarts that reset this map. *When:* with the general 429 work (see "Drawings / API" below) or when assist traffic actually grows.
- **Surface the AI-assist panel in `/play` too** — Phase A only mounts the prompt panel in `DrawView.vue`; the capability (prompt → validated ops → ghost preview → accept) is reachable only from the free editor, not the duel, though `packages/editor`'s shared `previewOps`/`acceptOps`/`rejectOps` API needs no change to serve `/play`. Wiring it into `/play` serves the AI-in-product north star directly (the game, not just the supporting mode). *When:* after the core `/play` loop stabilizes; needs a `/play`-appropriate UI treatment (the round timer/turn structure differs from free `/draw`).

## AI budget (`internal/aibudget`, shipped 2026-09-20)
Deferred on purpose during the 2026-09-20 adversarial review; each of these was proposed, weighed and parked with a reason.

- **A per-provider global ceiling** — `AI_DAILY_GLOBAL` is one number applied to every provider, so Google's free tier and the ML collaborator's own service (`collaborator`, `JUDGE_MODE=http`) share a figure that can only be right for one of them. Parked because the migration is genuinely cheap when it comes: the SAME variable absorbs `google=200,collaborator=50` the way `AI_DAILY_PER_USER` already does, with no second variable and no alias dance, and a bare integer stays valid as the degenerate case. *When:* the day a second provider is actually enforced (today every provider actually enforced is `google:<model>` — nothing yet runs under `JUDGE_MODE=http`, which is what would put the duel on `collaborator`).
- **A `Remaining(kind, userID)` port so the UI can say "1 guess left"** — a feature capped at **2/day** currently announces its limit only by refusing you. The ledger already answers the question (`CountUserKindCallsInWindow`), so this is a port plus a response field. The obviously missing seam rather than a defect. *When:* next touch of the guess or practice UI.
- **Rename `internal/judge` → `internal/vision`** — the package now holds three seams, **two of which are ours** (`Critic`, `Guesser`), and is named after the one that is not; both local files open with a banner explaining they are not what the package is called, which is the package telling you its name is wrong. `vision.Judge` still reads correctly for the collaborator's frozen contract, and `docs/JUDGE.md` keeps owning that contract regardless of the Go package name. Parked as churn mid-stream, but the cost curve only goes one way — every new seam makes it dearer. *When:* before a fourth seam.
- **A single-row ledger (`user_ids uuid[]`) instead of the provider-row/player-row split** — proposed in review as simpler: one row, one meaning, no CHECK constraint, no N+1 insert. Rejected because it loses the `users` foreign key entirely and needs a GIN index for `= any(user_ids)`, and because the two halves genuinely happen at **different moments** for a duel (a round is granted when the roster fills; the provider is called when the round ends, possibly more than once) — which is exactly what the two columns express. *When:* not planned; recorded so the question is not re-opened from scratch.

## Auth / identity
- **Login charset/format validation** — `login` is currently validated by **length only** (3–254 chars). Add format rules: if it contains `@`, validate as an email; otherwise restrict a nickname to `[a-zA-Z0-9_.-]` (no spaces, no emoji). This is the real gap (vs. the email/nickname *split*, which isn't needed). *When:* cheap — fold into the next auth touch.
- **Optional separate `email` column** — split the sign-in handle (`login`) from a verified contact `email`, unlocking password reset, email verification, notifications. *When:* only when an email flow is actually built (YAGNI until then). Until then the single `login` (email-or-nickname, citext, case-insensitive) stands as decided.
- **Product-grade auth surface (beyond the shared `AuthForm`)** (owner, 2026-07-11) — `feat/shared-auth-form` makes the sign-in form a shared component reachable inline on both `/play` and `/draw` (the auth *store*/`@core` client was already shared; only the *form UI* was trapped in `/draw`'s `SideMenu`). The **aspirational** upgrade is an auth experience that reads as senior product work. Candidates, roughly by impact: **(1) guest / anonymous quick-play** — jump straight into a duel on an ephemeral account, then optionally *claim* it (register to keep rating/history) — the biggest funnel win for a drawing-duel game and a strong product-thinking signal; **(2) a global, mode-agnostic auth affordance** — an app-shell "sign in" entry and/or a `/login` route + an accessible focus-trapped dialog (rebuild on `@oriui/headless` `useDialog`), so auth is a first-class cross-cutting surface, not a card per view; **(3) resume-after-auth** — sign in mid-flow and land back exactly where you were (the pending match), not a generic redirect; **(4) OAuth (GitHub/Google) and/or passkeys (WebAuthn)** — real-world identity integration, the most impressive but the most infra (needs the `email` column split + provider wiring); **(5) form-feel polish** — inline field validation, password-strength meter, distinct error/loading/success states, "remember me". *Why:* auth is the first thing a new user touches; a frictionless guest→claim flow plus real OAuth/passkeys is a standout, and it directly serves the game (less sign-up friction = more duels). *When:* after the core `/play` loop lands; sequence (1)+(3) first (cheapest, highest funnel value), (4) when an email/identity flow is actually built. Pairs with the `email` column split (above) and the `useDialog` dialog rebuild (Frontend / build).

## Drawings / API
- ~~**Rate limiting (429)**~~ — **DONE** (2026-09-18, `feat/ratelimit-reqid`, ROADMAP Phase 5): three per-IP token-bucket tiers (strict auth, moderate writes, generous default) in front of the mux, with `TRUST_PROXY` deciding whether `X-Forwarded-For` is believed, plus `X-Request-Id` correlation in the access log. This was the real remaining abuse vector for drawings (spamming valid-but-heavy documents), **not** SQL injection (queries are fully parameterized via sqlc; ownership is enforced in every `WHERE owner_id`).
- **Server-generated `thumbnail_url` only** — when thumbnails land, store **only** a server-side object-storage URL, never a client-supplied one (avoids stored-SSRF / XSS via a poisoned URL). *When:* when thumbnails are implemented (Phase 2/3).
- **One open match per user (concurrency hardening)** — the `FindMyOpenMatch` dedupe (`DECISIONS.md` 2026-07-03) is Read-Committed **best-effort**: a truly concurrent same-user double-tap can still open two `open` matches (never a double-*seat* — the composite PK guards that). Enforce hard with `pg_advisory_xact_lock(hashtext(userID))` at the top of the create tx, or a partial unique index. Was meant to fold into the rate-limit slice (same abuse class) — that slice shipped 2026-09-18 without it, so this is **still open** and no longer has a pass to ride along with. *When:* its own small slice, next time matchmaking is touched. *(jp-go + jp-security review, feat/game-matches.)*

## Game — judging & render
- ~~**Real render worker (Node Konva + perfect-freehand)**~~ — **DONE** (`feat/render-worker`): `render.StubRenderer` is replaced by the pixel-authoritative worker — `server/internal/render/node.go` (`NodeRenderer`) shells out to the bundled `packages/render` Node CLI, which renders the vector document off-client using the *same* Konva + perfect-freehand path as the editor (`RENDER_MODE=node`). Swapped in behind the `render.Renderer` interface with no game-loop change; unblocked a truthful judged raster. See `docs/ROADMAP.md` Phase 3.
- ~~**Judging durability sweeper**~~ — **DONE** (`feat/round-deadline`): `server/internal/game/sweeper.go` runs a boot-drain + periodic (3s) sweep that re-drives judging for any match stuck in `judging` (crash recovery, capped retries), alongside the round-deadline/forfeit sweep and stale-`open`-match reaping. See `docs/ROADMAP.md` Phase 3 / `docs/GAME.md` §4.1.
- **Object storage for `judgedImageUrl`** — the result reveal shows each player the *opponent's* canvas, which the ownership-scoped `GET /api/drawings/{id}` can't serve (foreign owner → 404). So `judgedImageUrl` must point at the server-rendered PNG in object storage, authorized by match-membership. Null until this lands. Store **only** server-side URLs (never client-supplied — stored-SSRF/XSS). *When:* with the real render worker. *(Already listed under Drawings/API as the thumbnail seam — same storage.)* **Superseded (2026-07-11):** `docs/ROADMAP.md` Phase 3 records this as deferred and no longer gating anything — the reveal ships instead via the membership-gated `GET …/players/{userId}/drawing` endpoint + a client-side render. Object storage remains a later, optional slice (feed thumbnails, render offload, signed judge URLs), not a blocker.
- ~~**Cross-match rating lost-update (`users.rating`)**~~ — **DONE** (2026-07-17, `feat/ratings-leaderboard`): the absolute `SET` (`UpdateUserRating`, now deleted) is replaced by `ApplyRatingDelta` (`rating = rating + delta returning rating`), so two concurrently-resolving matches sharing a user both land — the match `FOR UPDATE` lock serializes per *match*, not per *user*, so it never guarded this. `writeFinalResult` derives the `rating_before`/`rating_after` snapshot from the `RETURNING` and sorts players by `user_id` (deadlock-safe under a concurrent rematch). Advisory-lock (`pg_advisory_xact_lock`) was considered and rejected — the judged path reads ratings outside the tx, so a lock would force moving the read in-tx and recomputing Elo for no gain. Regression-proven by `internal/game/rating_db_test.go`. See `docs/DECISIONS.md` 2026-07-17 + `docs/NOTES.md`.

## Realtime (WS hub, `internal/ws`, shipped `feat/ws-realtime`)
- ~~**Server-side read-idle timeout + a symmetric server→client heartbeat**~~ — **DONE** (`feat/ws-hardening`): `internal/ws/conn.go` adds `heartbeatLoop`, a third per-connection pump that evicts a connection idle for `Limits.ReadIdleTimeout` (closing with private code `4002`) and, well under that budget, proactively probes the peer every `Limits.HeartbeatInterval` with a protocol-level ping — answered by the browser's network stack, not client JS, so a healthy-but-quiet duelist (mid-draw) is never evicted and no frontend change was needed. Both intervals are explicit `Limits` fields, never a hardcoded constant. See `docs/API.md` §9.1, `docs/NOTES.md`.
- ~~**A global connection semaphore / per-IP cap, beyond the per-user-per-match cap**~~ — **DONE** (`feat/ws-hardening`): `internal/ws/limiter.go`'s `connLimiter` adds a process-wide cap and a per-IP cap (both explicit `Limits` fields, keyed on `r.RemoteAddr` — never a client-supplied header), checked before `Accept` and refused as the existing `429 rate_limited` envelope. Independent of, and in addition to, `wsMaxConnsPerUser`. See `docs/API.md` §9.1.
- **Multi-instance hub via Postgres `LISTEN/NOTIFY` or Redis, behind the `Publisher` seam** — the in-process, single-goroutine hub (`internal/ws`) is a known single-instance ceiling: rooms/connections live only in that process's memory, so horizontal scaling would strand half of any room on the wrong instance. `game.Publisher` is the deliberate extraction point — swap the in-process fan-out for a pub/sub-backed one with **no `internal/game` change**. *When:* only if connection count or availability needs actually force horizontal scaling — explicitly out of scope for the current single-process deployment (deferred §5 Q8, `docs/DESIGN-PHASE3-LIVE.md`).

- **Color/size popover controls** — a two-swatch (stroke + fill) visual that opens a popover (not a modal) with the pickers, closes on click-outside, and blocks canvas input while open so a stray stroke can't land (legacy `ColorSettings`, `@vueuse` `onClickOutside`). **Where:** a cleaner `EditorToolbar` (move color/width into a collapsible settings card).
- **Auth-aware actions** — Save disabled until signed in; an inline login↔register toggle sharing one compact space; a saved-count badge (legacy `SaveArt` / `UserProfile`). **Where:** `SessionBar` polish.

## Design & UX ideas (from similar tools & games)
Researched 2026-07-02 from drawing editors (Excalidraw, tldraw, Figma/FigJam, Photopea) and drawing-duel games (Skribbl.io, Gartic Phone, Draw Battle, Jackbox Drawful). **Recorded only — not building now.** Grouped by surface; the game items serve the north star (`/play`).

**Editor & canvas (`/draw`, `packages/editor`)**
- **Bottom-docked / floating toolbar** — thumb-reachable, doesn't eat the canvas; adapts to a compact bar on mobile (tldraw, FigJam).
- **Zoom / pan / fit gestures** — pinch-zoom, two-finger pan, wheel+shift; `Ctrl+0` fit-all, `Ctrl+1` 100%. (This is the Phase-2 fit-to-viewport work — scale the Konva **stage**.)
- **Compact color control** — a preset swatch grid (~18 colors) + recent-colors history + a "more" button to the full picker; eyedropper (Alt-click) (Photopea, Sketchful).
- **Brush-size preview** — a live circle under the cursor / next to the tool showing size + opacity before drawing (Procreate, Photoshop).
- **Layer thumbnails** — mini previews per layer in the panel (Figma, Photopea) — pairs with the server `thumbnail_url` idea.
- **Visual undo-history** — a hoverable list of recent actions; click to jump back (Photopea History, Krita).
- **Shortcuts cheat-sheet** — a `?`/`Cmd+?` modal listing keys (Excalidraw, tldraw). Extra tools: fill-bucket, more shapes.

**Game — lobby & match (`/play`, Phase 3)**
- **Minimal lobby** — big prompt text, ready-up toggle (auto-start when all ready), live player-avatar list with ready dots; host settings via sliders (rounds, seconds/round, public/private) (Skribbl, Gartic Phone).
- **Centered prompt reveal** — the prompt appears center-screen ~3s at round start, then each player draws their own canvas (Gartic Phone, Drawful).
- **Round timer bar** — top progress bar, green→orange→red under 10s, with an alert cue (Skribbl).
- **Split view for spectators** — both canvases side-by-side for the audience; each player sees only their own during the round (Draw Battle).

**Game — result & rating (`/play`, Phase 3)**
- **Animated result card** — both drawings side-by-side, the ML similarity as a 0–100% bar, the judge's one-line reason, an arrow animating to the winner (Game UI Database, LoL victory screen). A `?` tooltip expands the judge's rationale (transparency).
- **Score pop + leaderboard** — floating "+15" juice on award; a leaderboard table (nick / avatar / score / Δ) highlighting the current player; a match-summary screen with Rematch / Share (Skribbl, Jackbox).
- **One-click share** — export the round (both drawings + result) as a PNG/GIF for social (Gartic Phone album, ShareX).

**Cross-cutting — theme, responsive, feel**
- **Dark-mode toggle** — moon/sun switch; oriui already ships both themes (also in the salvaged-legacy list).
- **Mobile portrait layout** — canvas ~70%, toolbar bottom, panels collapse to icon-tabs; primary actions in the bottom third for one-handed reach.
- **Game-feel polish** — smooth 200–400ms easings, toast notifications for match events, skeleton loaders while the judge scores, optional audio cues.
- **Playful brand type** — a hand-drawn display font (Excalidraw's Virgil / Caveat) for lobby & result headings to set a fun tone; keep a clean system/`Nunito` body.

*Priority for the game MVP:* bottom toolbar · compact color picker · animated result card · round timer · match summary · dark-mode · mobile layout. Editor polish (layer thumbnails, brush preview, zoom/pan) and juice (score pop, audio, replay) come after the core loop.
